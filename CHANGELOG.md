# Changelog

## [Unreleased]

### Added
- **A set-up screen instead of environment variables.** A new LeuffenDoc needs an image, a port and a volume, nothing more. The first visit opens a set-up screen that asks for a code printed in the container's log — so only whoever runs the container can claim it — and then for **one thing: the RMM's address**. Its own address, whether a reverse proxy is in front and which address it connects from, and https-only cookies are filled in from what the server sees of that request, and can be changed under **Zelf aanpassen**. Everything is kept in the database and changed later under **Instellingen**, which now also holds the proxy, cookies, the always-administrators and how long a sign-in lasts. Environment variables still work and win, for pinning a value or getting back in; a container started the old way skips the screen.
- **Linking with the RMM is one button.** **Koppelen met de RMM** sends you to the RMM, a global administrator approves, and both sides are set up: the RMM issues LeuffenDoc's API key and records LeuffenDoc's address on its side, and whoever approved administers LeuffenDoc and is signed in. The key never passes through the browser — the browser carries a single-use code, which this server exchanges with a secret only it holds (PKCE) over its own connection. When this server cannot reach the RMM at the address the browser used — a NAS that does not reach its own public name, a self-signed certificate — the page asks for one that works and tries again. **Instellingen** links again (another RMM, a revoked key), and so does the RMM's own **Link with LeuffenDoc** button. Needs the RMM with pairing; an older one can still be linked by hand on the same screen.
- **Tests that stop a broken release before it is built.** A test suite in the repository runs a real LeuffenDoc on a throw-away database and checks what matters most: the vault (sealing, tampering, fingerprints, strength), who may see and read what, share links, back-ups and putting one back, the export, and that the RMM never receives a password or anything shut off. GitHub Actions runs it on every push, and the image is only built when it passes.
- **A customer's documentation as a zip, to take away.** **Exporteren** on a customer's overview downloads everything you may see there: a page to read and print that opens without the server (machines with their hardware, adapters and switch ports, a switch with its patch list, procedures with their text, what is linked to what), the same as JSON, and a sheet per kind for Excel — semicolons and all, the way Excel on a Dutch machine opens it. For a customer who leaves, for an audit, or just to have it elsewhere. What is shut off to others stays out. **Passwords only when ticked**, only for someone whose role lets them read passwords, with a warning that the file then holds them readable — and each password taken along is a line in the log, like any other reading.
- **Back-ups that open, made while the server runs.** Copying the database file of a running server is not a back-up — the latest changes sit in a second file, and a copy taken mid-write can come back broken. LeuffenDoc now has SQLite make a consistent **snapshot** every `DOC_BACKUP_HOURS` (a day by default) into `backups/` in the data volume, and keeps the newest `DOC_BACKUP_KEEP` (fourteen); whatever backs up the volume picks up files that open. **Nu een back-up maken** does one on the spot. Both can be set under **Instellingen → Back-ups**, and a failed automatic one is shown there.
- **A back-up to take away is always encrypted.** **Downloaden** asks for a passphrase and hands out a `.ldbak` file: the database compressed and encrypted with AES-256-GCM under a key derived from the passphrase with scrypt, the header authenticated along with it. It has to be: a back-up holds every customer's documentation, and when `DOC_SECRET_KEY` is not in the environment, the key to the vault as well. The README says how to open one without LeuffenDoc.
- **Putting a back-up back, from the page, without a restart.** Upload a `.ldbak` (or a plain snapshot taken off the volume) and it is checked before anything happens: that it is whole, that it is a LeuffenDoc database, and that **its passwords open with the key that will be in force afterwards** — a back-up that would leave a vault nobody can open is refused, with the reason. **Terugzetten** then says what it will replace and replaces the contents in place. The state just before is kept as a back-up of its own, so putting one back can always be undone; nobody is signed out; and the RMM's Docs tab is brought in line with what is back.
- **What is documented here shows in the RMM's device drawer.** A **Docs** tab there has what was written down about the machine — installed on and by, warranty (flagged when it nears), location, notes — the **switch port** it hangs on, and the passwords, documents and people linked to it, by name, each opening its page here. It is sent from here over the API key LeuffenDoc already uses, so there is no second key and no way into this server to open. A change is in the RMM within seconds; a quiet round sends nothing, since only machines whose summary changed are sent. Passwords never go across, and neither does anything shut off to named colleagues — the RMM shows the tab to whoever may open the device. **Klanten** says whether it is working. Needs the RMM with the Docs tab; with an older one the page says the RMM needs updating.
- **Kluis: every customer's passwords at once, for an administrator.** Four lists, each answering one question: which passwords are past or near their **Vervangen vóór** date, which are **the same password in more than one place** — at the top when that spans customers, because a leak at one is then a leak at all — which are **weak**, and which have **not changed in a year** (the limit is under **Instellingen**, and can be switched off). Each line says whose it is and opens the password at its customer. None of it opens the vault: how strong a password is, and a fingerprint to compare it by, are worked out at the moment it is stored. The fingerprint is keyed with the vault's key, so a stolen database cannot be checked against a list of common passwords. Only the grade is stored, not the reason — "seven digits" in a column is a hint to whoever steals it. Passwords stored before this version are listed as not judged until an administrator presses **Nu beoordelen**, which opens them once on the server and writes one line in the log. Equipment taken out of use is left out.
- **A password says how strong it is.** *Zwak*, *matig* or *sterk*, next to its name, for whoever may read it. Weak means short, little variety, or a well-known word with digits after it — *Welkom2024!* is eleven varied characters and still found in seconds.
- **A password can be shared with someone who has no account.** **Delen** makes a link for a supplier or a customer's new employee, valid for an hour up to a week and for one to ten openings, with a note for whom it is. The link is shown once — only a hash of it is kept, and the password travels in a sealed copy of its own, which is dropped the moment the link can no longer be opened. The page behind it shows nothing until **Wachtwoord tonen** is pressed, because Teams, Outlook and Slack open a link by themselves to draw a preview, and that preview must not use up a link meant for one look. Two people opening a one-time link at the same moment do not both get it. Every opening is in the log with where it came from; the password's page lists its links with how often each was opened, and one still open can be withdrawn. **Changing the password closes every link still open for it**, so a new password never goes out through an old link. Needs `DOC_PUBLIC_URL`, and `/deel/` reachable from where the other person is.
- **A password can be shut off to named colleagues.** **Wie mag dit zien** on a password — or on any type of your own with password fields — is everyone at the customer by default; **Afschermen** narrows it to the colleagues you tick. For anyone else it does not exist: not in the list, not in search, not at the end of a link from the firewall it belongs to, not even in the customer's counts, and its page is reported as missing rather than forbidden. Administrators always see it. Whoever shuts something off stays on the list, so nobody locks themselves out of what they are standing on. Both the change and who could see it before and after are in its history.
- **What someone may do at a customer comes from their role in the RMM.** A **viewer** there reads the documentation here — everything, including that a password exists — but changes nothing and sees no passwords. A **member** or **admin** there may do both. Access was already administered once, in the RMM; now what that access allows is too, and changing a role there takes effect here on the next sync. The page does not offer a button the server would refuse: a reader sees *alleen lezen*, a password panel that says there is no access and where that is decided, and a notice when they open the customer. Every change and every reading of a password is checked on the server regardless. Needs the RMM that reports roles from access groups correctly.
- **Instellingen, for administrators.** What used to need an environment variable and a restart can now be set from the app: the link with the RMM (with a **Verbinding testen** that says which part fails), Microsoft 365, the public address, and when a date starts to warn. The RMM's API key and the Microsoft 365 client secret are stored sealed with the vault's key and never sent back to a browser — the page shows only whether one is set and its last four characters. A value fixed in the container's environment is shown but not offered, with the variable named. Configuring the RMM link from here starts syncing straight away, without a restart. What decides whether anyone can reach the page — the proxy, cookies, the bootstrap administrators — is shown for reference and stays in the environment.
- **Settings for the password generator.** Length, which kinds of characters, which punctuation (some routers refuse a quote), whether to leave out characters misread off a screen, and whether every kind must appear at least once so a password always meets a rule like “at least one digit”. An example on the page follows the form as you change it. How long a shown password stays visible is set here too.
- **Updating from the page, like the RMM.** **Over deze server** pulls the newest image, says which version is waiting, and replaces the running container on it. It keeps ports, volumes, networks, the restart policy and the settings given to the container, but takes the command, health check and built-in defaults from the new image. The previous version is only discarded once the new one reports healthy; if it does not start, the previous one is put back and the page says so rather than reloading as if it had worked. Needs the Docker socket and an image from a registry; without them the page says what is missing. The image now carries a health check and its version as a label.
- **Types you define yourself.** The built-in kinds cover equipment and a customer's own parts; everything else an MSP writes down — a Microsoft 365 tenant, a backup job, a certificate, a domain — differs per shop, so it is defined under **Documenttypes** instead of guessed at. A type is a name, an icon, a sentence about what it is, and a list of fields: text, long text, number, date (optionally one that warns you when it nears), a choice from a list, yes or no, an IP or MAC address, several labelled values, a reference to anything else, and **passwords**, encrypted like the vault and several per item if you need them. You pick which fields show in the list. The moment it is saved, every customer has a section for it.
- **A type of your own gets everything the built-in ones have**, without a line of code knowing it exists: its history names the fields the way you named them, it is searchable, it can be linked, its references are read from both sides, its dates come and find you on the customer overview. Removing a field that is filled in says which one and how often before anything is lost; a type still in use cannot be deleted until nothing is left of it.
- **The customer list shows which customers the RMM knows.** A linked customer carries the RMM's own shield on its mark, and says so in words underneath; one that exists only here says that instead. On a list of twenty customers the one that is *not* linked is usually what you are looking for, and a badge is quicker to scan than a line of text. The customer's own page carries the same mark.
- **Several addresses and numbers per contact.** One phone number per person is a fiction: there is a desk number, a mobile, and the one that is actually answered. A contact now takes as many e-mail addresses and phone numbers as it needs, each with what it is for (*Werk*, *Mobiel*, *Facturatie*), shown on their own lines rather than run together.
- **Icons on the lines you scan for.** A memory module next to the memory, a disk next to the disks, a processor, a telephone, an envelope, a globe for an address. Not on every field — an icon beside everything is the same as none — but on the hardware, the ways to reach someone and the network, which is what you are looking for when you are not reading.

### Changed
- **Network adapters and switch ports are edited with the configuration they belong to.** They used to have their own buttons on the page, each committing on its own. Now the page *shows* them and **Bewerken** changes them: the MAC, the VLAN and the switch port sit in the same form as the rest of the machine, and one **Opslaan** saves all of it. The same on a switch, where editing makes the port labels and VLANs editable and lets a port be emptied. What the RMM reports stays shown rather than offered, since typing over it would only last until the next sync.
- **Documents, for what does not fit in fields.** A procedure, an explanation, what to do at three in the morning when the VPN is down. The text keeps the line breaks and the indentation it was written with — the indentation of a command in a procedure is part of the procedure — and gets the width of the page rather than a label column. Every version is kept, so an edit can be undone; the history says *what* changed and how much, without reprinting the whole document. A document hangs on the machine it is about, like anything else, and carries a **Nakijken vóór** date, because documentation nobody rereads starts lying quietly.
- **Search across every customer you may see.** In the header, or **Ctrl/⌘ K**. It looks in names, in every filled-in field, in what the RMM reported, and in the **MAC and IP addresses of network adapters** — because the question is usually the other way round: you have a serial number or a MAC in front of you and want to know whose it is. Each result says which customer it belongs to, where it matched, and shows the sentence around the match. Passwords are findable by name and by what they are for; their contents are not searchable at all.
- **The password vault.** Passwords live next to the thing they open: a password is an item like any other — same history, same access, same links — so you hang it on the firewall it belongs to and find it there, instead of in a separate list nobody opens. The password itself is **not** a field: it is encrypted in its own table, because fields travel through every list and land in the history as *“from this to that”*, which is exactly what a secret must never do.
- **Encrypted in two layers.** Each password gets its own random key, AES-256-GCM; that key is stored wrapped with the master key. Replacing the master key then means rewrapping small keys rather than rewriting every secret, and a tampered record fails to open instead of returning something plausible. The master key comes from `DOC_SECRET_KEY`; without it one is generated and kept in the database, and **Wachtwoorden** says so plainly — an operator should know whether a backup holds both the vault and the key that opens it.
- **Every reading is one line in the log.** A password leaves the server only when asked for by name, one at a time, and each time it is written down with who and from where. The page shows dots until you press **Tonen**, hides it again by itself after thirty seconds, and **Kopiëren** puts it on the clipboard without showing it. There is a generator (twenty characters, no lookalikes) for when you are setting one rather than recording one. The history says a password was set or changed and when — never what it was, nor how long.
- **A reference is written once and read from both sides.** A computer names its location; standing on the **location**, you now get *“Wat hier staat”* — the machines, the printers, the people, the lines — grouped by how each one points at it, and clickable through. The same on a **contact** (*“Waar deze persoon bij hoort”*) and on a **firewall or router** (*“Wat hierop aangesloten is”*, which is where the internet connections show up). Nobody writes that list; it is the other half of what was already filled in. Equipment taken out of use stays on the list, marked, because “what used to be here” is a real question.

### Fixed
- **After a restart, settings saved on the page were treated as if they came from the environment.** The start-up script copied every saved setting into the process environment, so after a restart the settings page showed them as fixed and would not let them be changed — and the RMM's API key, stored sealed, was used sealed, which broke the link with the RMM until someone noticed. Nothing is copied any more; the environment is what the container was started with. Which proxy to believe is now decided per request by the app rather than once by the web server at start-up, which is what lets it be set on a page.
- **Every sync with the RMM made every machine look freshly edited.** A sync that found a machine exactly as it was still stamped it as changed just now, by nobody. Only a change that moves something counts now, so *last changed* means what it says.
- **A tab left open kept showing what was true when it was opened.** The page reused what it had fetched about a customer, so something another person added, changed or opened up did not appear until you reloaded. Opening a list, a page or the overview now fetches fresh.
- **A field could not be emptied.** Clearing a value in a form and saving left the old one in place: the payload was cleaned of empty values before it was stored, so the clearing never arrived. A field the person deliberately emptied now stays empty, and the history records it as such.
- **Deleting something other pages point at is refused**, naming what still refers to it and pointing at **Afvoeren** instead — which keeps those references intact.
- **Network adapters, and the switch port each one hangs on.** A machine carries its adapters with their **MAC addresses** — straight from the RMM for a machine with an agent, by hand for a printer or anything else. On an adapter you pick a **switch** (itself a configuration here) and a **port number**, and that one act is visible from both sides: the machine says *“SW-KERN, poort 6”*, the switch shows its **whole patch list** — what is on each port, with which label and VLAN, and **which ports are still free**, which is what you actually came to look up. A port cannot be claimed twice; trying says what is in the way, and a port the switch does not have says how many it has. Moving a cable empties the old port instead of appearing on both. Adapters are matched on their MAC, so an interface renamed on the machine keeps the port it is patched into.
- **Machines from the RMM document themselves.** Every device the RMM knows becomes a configuration in the right customer, and its **processor, memory, disks, operating system, make, model and serial** come from there and stay in step — shown on the page, never typed. More memory in a machine shows up by itself, *and lands in the history* as “Geheugen 16 GB → 32 GB” with the RMM as the one who changed it. What the RMM cannot know stays yours on the same page: when it was installed and by whom, the warranty, the location, notes. Rename it or correct what kind of machine it is and the next sync leaves that alone. A device that **disappears from the RMM** keeps its page, says since when, and offers to take it out of use — what you documented about a machine is usually exactly what you need after it is gone. Without an RMM none of this runs and every field is simply typed, which is what LeuffenDoc on its own looks like. Requires the RMM server that carries the hardware in `/api/v1/devices`.
- **An expiry date for equipment, that comes and finds you.** Computers, network gear and printers have a **Verloopt op** date for when they should be replaced or written off. It sits in the list, and anything expired or within sixty days is flagged there, on the page itself, and at the top of the customer's overview with a way straight to it. The same goes for a warranty running out and for an internet contract about to renew itself.
- **Out of use is one thing, in one place.** Equipment that leaves is **archived** — out of the lists, still there behind “toon afgevoerde”, with everything documented about it intact. “Afgevoerd” is no longer also a status you can set, since two places for one fact is how a list ends up disagreeing with itself.
- **Configurations, and the customer's own parts.** A customer now holds what you actually document: **computers and servers**, **network equipment** and **printers** as configurations, and **internet connections**, **locations** and **contacts** as their own sections, because those are not equipment. Each kind has its own fields — a computer carries its processor, memory, disks and operating system alongside *when it was installed and by whom*, its purchase date and its warranty; an internet connection carries the provider, the line, the fixed IP block, the contract and the number you ring when it goes down. The forms are built from one catalogue the server hands over, so a field added there appears in the interface by itself. Fields the RMM knows are marked as the RMM's and cannot be typed here, so a documented memory size can never quietly disagree with the machine.
- **Everything is related to everything, and remembers what changed.** Any two things belonging to the same customer can be linked — a line to the firewall it lands on, a location to the machines in it — stored once and shown from both sides. Every change records who made it, which field moved and from what to what, and any single change can be undone from the page; the undo is recorded like any other change rather than rewriting what happened. Equipment that leaves is **taken out of use**, not deleted, because the documentation hanging off it is usually exactly what you need a year later.
- **Signing in with your RMM account, and customers that come along with it.** LeuffenDoc sends you to the RMM, which already knows who you are — or asks you to sign in there, with the 2FA and IP rules it already enforces — and sends you back with a single-use ticket. LeuffenDoc redeems that ticket over its own connection with its API key, so the ticket alone is worth nothing to anyone who finds it. Your customers and whether you administer them come across in the same answer, and are refreshed every 15 minutes, so access granted or withdrawn in the RMM needs no second administration here. **Klanten** shows the state of that link and can sync on the spot. **Microsoft 365** works alongside it as the way in when the RMM is unreachable, or for someone with no RMM account; they arrive without customers, which an administrator grants here.
- **Runs behind your reverse proxy, and says so when it doesn't.** TLS is terminated by the proxy, as with the RMM. Forwarded headers are believed **only** on connections from the address you name in `DOC_PROXY_IPS`, so nobody reaching the container directly can write their own address into the audit log — and the proxy must *overwrite* `X-Forwarded-For` rather than append to it, since the oldest entry in an appended list is whatever the visitor's browser felt like claiming. **Logboek** shows the address the server sees you arriving from and names anything that is off: headers not passed on, a missing public address, a cookie the browser will refuse, or a proxy that any caller could impersonate.
- **The foundation.** LeuffenDoc runs as its own container next to the RMM: SQLite storage, signed session cookies, customers, an audit log that everything else will write to, and the interface shell in the same design as the dashboard. It has two levels, because documentation only means something in the context of a customer: the start is the customer list, and a customer's documents and passwords appear once you are inside one. Only what genuinely spans customers — the shared document types and the log — stays at the top. Where you are is in the address, so the back button, a refresh and a copied link all land where you expect. Signing in through the RMM and with Microsoft 365, the documents themselves, customisable document types and the password vault are built on top of this, each in its own step.
