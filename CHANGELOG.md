# Changelog

## [Unreleased]

### Added
- **Configurations, and the customer's own parts.** A customer now holds what you actually document: **computers and servers**, **network equipment** and **printers** as configurations, and **internet connections**, **locations** and **contacts** as their own sections, because those are not equipment. Each kind has its own fields — a computer carries its processor, memory, disks and operating system alongside *when it was installed and by whom*, its purchase date and its warranty; an internet connection carries the provider, the line, the fixed IP block, the contract and the number you ring when it goes down. The forms are built from one catalogue the server hands over, so a field added there appears in the interface by itself. Fields the RMM knows are marked as the RMM's and cannot be typed here, so a documented memory size can never quietly disagree with the machine.
- **Everything is related to everything, and remembers what changed.** Any two things belonging to the same customer can be linked — a line to the firewall it lands on, a location to the machines in it — stored once and shown from both sides. Every change records who made it, which field moved and from what to what, and any single change can be undone from the page; the undo is recorded like any other change rather than rewriting what happened. Equipment that leaves is **taken out of use**, not deleted, because the documentation hanging off it is usually exactly what you need a year later.
- **Signing in with your RMM account, and customers that come along with it.** LeuffenDoc sends you to the RMM, which already knows who you are — or asks you to sign in there, with the 2FA and IP rules it already enforces — and sends you back with a single-use ticket. LeuffenDoc redeems that ticket over its own connection with its API key, so the ticket alone is worth nothing to anyone who finds it. Your customers and whether you administer them come across in the same answer, and are refreshed every 15 minutes, so access granted or withdrawn in the RMM needs no second administration here. **Klanten** shows the state of that link and can sync on the spot. **Microsoft 365** works alongside it as the way in when the RMM is unreachable, or for someone with no RMM account; they arrive without customers, which an administrator grants here.
- **Runs behind your reverse proxy, and says so when it doesn't.** TLS is terminated by the proxy, as with the RMM. Forwarded headers are believed **only** on connections from the address you name in `DOC_PROXY_IPS`, so nobody reaching the container directly can write their own address into the audit log — and the proxy must *overwrite* `X-Forwarded-For` rather than append to it, since the oldest entry in an appended list is whatever the visitor's browser felt like claiming. **Logboek** shows the address the server sees you arriving from and names anything that is off: headers not passed on, a missing public address, a cookie the browser will refuse, or a proxy that any caller could impersonate.
- **The foundation.** LeuffenDoc runs as its own container next to the RMM: SQLite storage, signed session cookies, customers, an audit log that everything else will write to, and the interface shell in the same design as the dashboard. It has two levels, because documentation only means something in the context of a customer: the start is the customer list, and a customer's documents and passwords appear once you are inside one. Only what genuinely spans customers — the shared document types and the log — stays at the top. Where you are is in the address, so the back button, a refresh and a copied link all land where you expect. Signing in through the RMM and with Microsoft 365, the documents themselves, customisable document types and the password vault are built on top of this, each in its own step.
